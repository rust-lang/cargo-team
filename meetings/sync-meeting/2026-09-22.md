## Cargo fix debrief

Ed: There's a GSoC project to try out a different architecture for cargo fix. Currently it's a rustc wrapper. The alt architecture is have cargo fix call cargo check and take everything at that point. The logic for figuring things out became a lot smarter since. If there's too independent packages they should be able to be fixed in parallel. The main cost is all the dependents build. We could do the "dangerous" mode to fix everything and then call cargo check afterwards. I plan to put this under an unstable feature in cargo.

Josh: Will the new approach work for `cargo clippy --fix`?

Ed: It has a `--clippy`. I think cargo clippy just forwards to cargo fix so that should automatically apply to clippy.

## Give each artifact dependency declaration its own features

* https://github.com/rust-lang/cargo/issues/17440
* See also
  * https://github.com/rust-lang/cargo/issues/11547#issuecomment-1430213596
  * https://github.com/rust-lang/cargo-team/blob/e2fd6c3fd/meetings/sync-meeting/2023%20H1.md?plain=1#L753-L757

Jacob: Artifact dependencise are a feature that let you depend on the build output of a crate. Does that cargo build of "foo" generate its dependencies as my dependencies, or does it have a more independent set of dependencies & features? The mental model we choose affects the usecases.

Ed: A related feature: opaque dependencies. A subgraph of dependencies has its own lockfile and feature resolution. Useful for embedded folks to build their firmware and include. It could also have settings for build scripts. Also, can help with runnable dependencies e.g. with sqlite where you need to keep them in sync.

Josh: Previously thought there was value in unifying between (for instance) a tool generating code/data/etc and a library working with that, to make them match. E.g. a protobuf tool and a library working with protobuf.

Josh: Nathaniel pointed out a more common case, which is that the tool depends on a library you also use, and its desired features and your desired features are *unrelated* and potentially counterproductive. Made worse by mutually exclusive features (which exist, even if we'd rather they don't). Or, conversely, if you have an embedded firmware, that firmware doesn't want to have a feature turned on just because *you* do.

Josh: I think there's value in unifying potentially, but we shouldn't unify by default.

Ed: Feature unification is confusing already. Adding a special case will be even more progblematic. We shouldn't be designing mutually exclusive features. Re embedded firmware: this would be like build/target separation: each target gets its own feature resolution.

Josh: Embedded may often be an x86 running on a host. Just because it's an embedded firmware it doesn't mean it's a different target than your host. But if you're building for a standalone target, that will work.

Ed: I think the proper fix would be opaque dependencies.

Josh: I think we should have opaque dependencies. But I think we should make artifact dependencies to be opaque by default.

Ed: Is that the right choice for to delegated build scripts?

Josh: I don't know.

Ed: Also, Josh you mentioned a tool like protobufs (library + binary). Under either model their features won't be unified. But we'll run into a proc macro problem, they might be generating code using the same features so the features may need to be unified anyway.

Josh: Features are the wrong mechanism for matching a format on the either side of the binary.

Weihang: Sounds the proposal is don't unify at all. What if there are 2 artefact dependencies that have a shared dependency. Should we try to unify them then?

Jacob: I'd think you'd have our normal situation where the feature resolution might not know about cashing, but later on cashing can figure out they're the same.

Ed: That should be unobservable from the outside, just for potential build-time improvements

Josh: I think you're making a compelling case for opaque dependencies to this. If someone came in to do opaque dependencies, how do you feel like this?

Ed: build-std will have something like this, so we may need to just generalize that work.

Ed: What are opaque dependencies: The gist is: we run everything in the same profile mode. But when you're building something like Unity, there are depencies that you may not even see inside. E.g. with gitoxide, gix could be an opaque dependency. We use its lockfile but we don't try to unify the features.

Jacob: This doesn't have an RFC. An opaque dependency can just be a blob with a set configuration. It may hit roadblocks.

Josh: Trying to manage scope: I think opaque deps are much harder for libraries than binaries. Would you consider it reasonable to only support compiling binaries at first?

Ed: If there's a simplification, yes, but I don't think it will help with the problems libraries will run into. There's also the `log` problem: log has a singleton to be used across crates.

Josh: I'm suggesting that's exactly the usecase for which making it binaries are not issue. It could never be linked twice to the same binary.

Ed: If this doesn't have issues with artifact deps, then I don't have a problem with this. The path to stabilization would be solve build-std, then artifact deps, then binaries(??).

Jacob: This needs an RFC

Ed: The build-std RFC was a proto-RFC for this. We need to work on the design.

Jacob: It help to do some long-range planning for this and have it expressed so we don't stabilize something slightly differently than what you need when stabilizing the whole thing

Ed: That was my concern with build-std and we've improved that

Ed: Josh, build-std is going to be an implicit opaque dependency we'll never make non-opaque.

Josh: I think I agree we need opaque dependencies and this is just hacking them into artifact dependencies.

Ed: For any of this work, we need to have at least a sketch of where we're going.

Jacob: Another option if we get stuck: we could require labeling even though it's only one option. You'd need to specify the dependency option even if there's only a single option and we can add other options. And if we decide on a default, we can add it then -- because before that not specifying it was an error.

Ed: There's still one limitation. If you have 2 different binaries set to cross-compile for the same target, the features for those binaries will be unified.

Josh: That's a good argument for having explicitly opaque dependencies

Ed: THey'll help with transitive dependencies but the actual applications will be unified

Josh: Knowing one of your primary applications is delegating build scripts, I appreciate your desire to unify them by default. That can improve the build performance. I'll bring this up to the issue.

## Asymmetric tokens

But following the security issues this weekend, there was an interest in reviving this. I'll be talking to Jess Izen today about that. Wanted to make sure everyone's happening.

Josh: I'd love to see us do asymmetric tokens. I've no attachment to the particular implementation we have now. And I don't have an employer who pays me to work on that anymore. The current half-done implementation should not block people who are actively working on things closer to shipping.

Arlo: One of the biggest issues was there was never work done on the server side on crates.io. We'd need more cross-team interaction.

Ed: I feel we'd get an order of magnitude improvement to do the deprecation of plaintext token storage

(everybody agrees)
