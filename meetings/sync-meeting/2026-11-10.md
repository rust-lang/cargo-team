## Modeling downstream registry divergence

Jess and Celina want to vibe check with the team about https://github.com/jlizen/goals/pull/1/

Jacob: Source replacement is being used for lots of things that it wasn't intended for. We are a different product than we were 10 years ago. This a draft RFC to rewrite our policy about source replacement. This RFC is an interesting vision doc, but we need to continue to iterate after.

Ed: Depending on how TUF is done, people abusing source replacement will not be possible.

Jess: WRT TUF, happy to add a section on how it relates to TUF. As a registry operator, I've been uncomfortable with how far we've diverged. I don't think crates.io will use this functionality. Focus on the goals section. Plan is to document the current reality including linux distros, JFrog, corprate users. What are people doing today? Want to focus on provanance. Auditing divergence is the goal. Interested in TUF things that we need to account for. We can adjust the goal as needed.

Ed: Caution about artifactory: they are also doing other weird things that are basically dependency confusion.

Jess: will start with linux distros.

Arlo: happy to talk about TUF requirements.

Jess: I've talked to RedHat, lightwell? Don't have a story for Rust yet.

Josh: Initial vibe is we should do something about this, and source replacement has been a giant hammer. I'm all for restricting this functionality to situations where it's actually needed. Appreciate that divergance is an attack unless declared. Should not be allowed to say you're a mirror of crates.io without actually doing that. Matching what Linux distros do might not actually be the best either. We should have an extra digit in the semver version to allow local patching.

Jess: semver issue is mentioned in the goal proposal

Jacob: Want to bring up that nomenclature terms are overloaded. Downstream: I change what's in crates.io. Mirror: if I'm not the same as upstream, then it's a security incident. This feature is about tampering with registries. We already have patching (client side), but this is server-side.

Ed: We've talked about the idea of registry-provided patches. There is interest in this. Our RFC process should be focused on exploring solutions. Worried that a lot of work went in to the sketch, so there can be a lot of attachment to the current approach. Would prefer that the RFC process started with the exploration and alternative exploration. Concerned about adding new fields to semver. Author of semver (Steve Klabnik) recently considering updating semver. This might be something to explore. Adding a 4th version field could cause a lot of problems. One option is an extra field, another is a post-release area. Would like more exploration by talking to crates.io or the semver folks. Want to keep a broad view to start. 

Jess: Likes the current RFC format, suggest we table conversation. This is a project goal, not an RFC. Need a champion (Arlo?). 

Josh: Want to distingiush between partial mirrors that are pure subset of crates.io and invalid mirrors. There's something useful about "I'm a valid mirror of the subset that I mirror". Companies may want to have a vetted subset, and one day we'll be so large that some mirrors may say "we carry the top million packages, get the rest from upstream".

Celina: is there an RFC for the TUF mirroring

Arlo: Yes, but it's somewhat out of date. New RFC coming soon.

Celina: There is a need to do something now. Don't want to hack on something that will be unsupported.

Ed: You're more documenting your current polyfill?

Celina: No, we're exploring how we can implement based on Cargo today. Build metadata seemed cleaner, but it doesn't work with older versions of Cargo (pre 1.75). For internal, we just want to avoid shooting ourselves in the foot.

Jess: We'll adapt our internal usage to align with the solution that the RFC comes up with. This is meant to be the long-term goal.

## Feature activation syntax

See https://internals.rust-lang.org/t/attempting-to-clean-up-the-feature-activation-syntax/24718
- Idea good?
- `foo?/bar` or `dep:foo?/bar`?

Ed: Our feature selection syntax is difficult to implement and requires global knowledge?
If you have `foo?/bar`, foo has to be an optional dep. Wants to change `foo` so it can be a required feature.
Should we move to to dep: `foo?/bar`. Feels noisy to have to type on the CLI. Want to deprecate `foo/bar`.

Josh: Want to make `a/b` the same as `a?/b`?

Ed: Possible thing to explore in future.

Josh: Seems like the ideal place to get to. Forcing people to write `?/` every time feels awkward. If we could move towards `foo/bar`, if you want to activate foo, you also have to write `dep:foo`. Should we move in a direction that makes features and packages more differentiated? 

Ed: That's the important part of the `dep:` syntax. The current status quo is confusing. We need a syntax that can work across editions. May need a intermediate situation where we don't allow `foo/bar` in order to do the migration.

Josh: steering towards the new mindsets makes sense, but why do we need something that works across editions?

Ed: edition migration. Standard procedure is to opt-in before changing the edition.

Josh: Suggesting that the way way to spell foo/bar, is `dep:foo, foo/bar`.

Ed: `foo/bar` is a mess. It can also activate features.

Jacob: Would a table (feature, dependency, optional dep, syntax) be helpful?

Ed: I have a list, but a table may be helpful.

Ross: Yes, table would be helpful.

Ed: Agree that it's complex.

Jacob: Table also needs `edition`.

Josh: vibe: appreciate the concept of having a migration. Concern is that we have everyone move to something, then move again -- some people will say "thanks for the transition period", and others will be annoyed by changing things too many times.

Ed: that expands the scope. Was hoping to have this fixed in time for implicit features.
