## 2020-12-01
- RFC serve crates-io registry over HTTP as static files
    - https://github.com/rust-lang/rfcs/pull/2789
    - https://github.com/rust-lang/cargo/pull/8890
    - concerns: 
        - caching causing inconsistency
            - Possible requirements:
                - Be able to send a project (with `Cargo.lock`) to another user, and it should work, even if they hit a different data center.
                - Should be able to publish mulitple packages that depend on one another in series, without needing to wait too long.
                - Cargo shouldn’t barf if a new package references a new dependency that isn’t found due to caching. (Should be OK, Cargo ignores packages that have missing dependencies.)
        - code signing, mirroring (such as China)
            - The current design would require signing each individual file.
            - Concern that signing is incompatible with the fundamental design of the RFC.
        - Use hashed filenames: Only root node would need to be signed, and deal with caching
            - All hashed filenames could have maximum TTL
            - Concern that if there is a root node that scales with the number of packages in the registry.
            - concern: content-hashed filenames would grow with each publish. pietro: would only need to retain older files for some limited period of time (~1 week?). 
        - Cloudfront support: costs should likely should be ok
        - There’s uncertainty about how long the GitHub solution will last.  
            - Would be interesting to know how often there are full clones vs incremental updates.
    - Adding a “snapshot” file could be added as an independent thing.
    - Would like to see the RFC to have some discussion of:
        - caching: the impacts, what the requirements are, etc.
        - signing: how feasible it is to add signing to the design
    - The rollover design of the changelog is quite complex and tricky. A snapshot would avoid those complexities.
