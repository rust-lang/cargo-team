Josh: Can we have an automated way to have a PR auto-open with the subtree changes shortly after nightly so we can simply just hit merge to make the breakage windows as short as possible

Scott: Cargo is special, and perhaps Cargo derserves this block-ability

epage's notes:
- On potential problems
  - Feels like the problems are solved today by spoken and unspoken conventions
  - While most problems seen today are error message updates, not all are and the goal is to accelerate those others (like changing Z flags)
- concern over sync work
  - have a MiR and someone partially paid to work on Cargo but shouldn't be dependent on that
  - conflicts are the minimum required pain to deal with and not great to require someone to manage
  - not helped if we push more on the person handling syncs like
    - resolving of test failures
    - applying "review feedback" that wasn't applied
- What is the actual bar for reverting a rust-lang/rust change due to Cargo conerns (qualiy, style, etc)? Perceived bar due to social pressure?
  - A revert would put the cleanup burden on the submitter, rather than the person babysitting the sync
- What tests should be run?
  - current build
  - stable
  - nightly?
- how do we handle nightly tests?
  - Currently, rust-lang/rust runs cargo's tests but not nightly, causing CI failures in cargo (imo those should never happen)
  - Ideally, they would run nightly tests
  - Ideally, contributors don't have to handle supporting old and new syntax to have a cargo transition
  - Idea: run nightly tests on nightly, forcing a transition
  - Idea: do nothing, sync will fail until the nightly, CI will fail until the sync
  - Idea: pin nightly, updated with the sync
    - want people to use stable by default, so not a root `rust-toolchain.toml` file
    - scripts to use the specified nightly? Or a non-root toolchain file that people can symlink into the root by gitignoring the file
    - does a sync always cause git history noise? If not, this will cause it. How do we feel about that?
- Why is cargo special?
  - Support more and different releases today
  - Cultural difference
    - Clippy/compiler have overlapping members to encourage similar culture
    - Some team combos might be too decoupled to run into cultural differences
    - Some differences with cargo/compiler come from isolation
    - However, some come from team size, some are because of the difference in our product (like our compat guarantees may be different)
    - Some push, pull, and intentionally divergent
- Blocking reviews
  - Should it actually block?
  - How would rust-lang/rust people respond to us being "special"?
  - Thoughts on blocking all but test changes to not have test output change problems?
- Possible action items
  - Codeowners?
  - Have cargo's nightly tests run against x.py's build (before or after migration?)
