- Profiles: target vs mode vs profile
    - [https://github.com/rust-lang/cargo/pull/6989](https://github.com/rust-lang/cargo/pull/6989)
    - For the named profiles PR, an issue came up with how the default profile works. Today it is somewhat complicated, but intended to be "intuitive".  The profile depends on the command (`build`, `test`, `bench`, etc.), the target (a "test" target or a "lib" target), and the profile (`--release`).  Walking through my logic:
        - `cargo build --test foo`  builds test "foo" with the "test" profile. I think this is relatively unsurprising.
        - `cargo build --all-targets` also builds test "foo" with the "test" profile, because I think it would be a little confusing if it was inconsistent with the previous point.
            - `--all-targets` builds lib/bins/deps with the `dev` profile, so different things use different profiles in the same command.
        - So with named profiles, what should `cargo build --all-targets --profile=foo` do? My thought is that everything should use the `foo` profile. 
            - But now we have a strange situation where a bare `cargo build` uses wacky profile selection, and `--profile` builds use a uniform profile.
    - This confusion can carry on with other commands.  `cargo test` builds the test with the `test` profile, but all dependencies are built with the `dev` profile.  This helps avoid rebuilding the world if `dev` and `test` diverge.
        - Should `cargo test` use just one profile for everything, or should it continue to use multiple?  What about `cargo test --profile=foo`?
    - Caveat: It appears to be extremely rare that projects have test and dev use different settings, so this doesn't affect most projects.

- Should the profile behavior for "test" be changed?
    - As part of proposed RFC: [https://github.com/rust-lang/rfcs/pull/2678](https://github.com/rust-lang/rfcs/pull/2678)
    - Currently the "test" profile only applies to the final test artifact. Dependencies use the "dev" profile. This can cause confusion:
        - The lib linked into an integration test will *not* use the "test" profile (it is a dependency).
        - [https://github.com/rust-lang/cargo/issues/4438](https://github.com/rust-lang/cargo/issues/4438)
        - [https://github.com/rust-lang/cargo/issues/6522](https://github.com/rust-lang/cargo/issues/6522)
    - The downside is that if `[profile.test]` is different from `[profile.dev]`, it will cause `cargo test` to recompile all dependencies.
        - The above RFC would mitigate this a little with `test` inheriting the settings from `dev`.
    - I think simplifying this would reduce confusion and give people more control.  If they want to avoid recompiling dependencies, then they can use `[profile.test.overrides."*"]` to force the dependencies to be shared with `dev`.
- Thoughts on renaming `overrides` to `dependencies`?
    - `[profile.dev.dependencies.image]` vs `[profile.dev.overrides.image]`
    - https://github.com/rust-lang/rust/issues/48683#issuecomment-483665255
    - “dependencies” may not be clear since it can also refer to the current crate.
