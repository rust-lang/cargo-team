Arlo: We should at least discuss the alternative of looking at all the values and try to add a tri-state value so people can go back to default.

Ed: I don't want a reset key `reset = ...` as proposed

Ed: Arlo, what you're saying is that we'd add reset functionality on a case-by-case basis?

Jacob: And going forward we'd have a checklist to decide about the reset value

Weihang: What can we reset today?

Arlo: [build.jobs](http://build.jobs/)

> Sets the maximum number of compiler processes to run in parallel. If negative, it sets the maximum number of compiler processes to the number of logical CPUs plus provided value. Should not be 0. If a string default is provided, it sets the value back to defaults. 

Scott: How does this work with the whole idea of "user config"? It would be interesting to be able to say "reset everything"

Ed: User is at the lowest-level compared to everything else. User is on top of defaults, then it's environment variables and commandline

Ed: That would be an elegant way of handling that.

Weihang: And stop config probing as a solution

Ed: Are you saying having also a "reset = all" flag inside of it?

Scott: Yes. Otherwise I need to know that the repo updated their cargo/config file and I'd have to update my local config to reset that.

Ed: It might be messy trying to define this. It makes me think of CSS

Jacob: Everything added to CSS was there to solve a real usecase. Maybe we should learn from it
