## (backlog) "cargo install" apparently ignores "Cargo.lock" as opposed to "cargo build"

https://github.com/rust-lang/cargo/issues/7169

Previous discussions
- https://github.com/rust-lang/cargo-team/blob/main/meetings/sync-meeting/2021.md#2021-02-02
- https://github.com/rust-lang/cargo-team/blob/main/meetings/sync-meeting/2022%20H2.md#2022-08-02

epage:
- being unlocked:
  - if a package has pre-built binaries, they need to re-release anyways, so the point is moot
    - today with github actions and releases as well as `cargo binstall`, many more projects have pre-built binaries than before especially if they will be used in CI
    - those without pre-built binary are likely to be limited in use
  - Even without `--locked`, user pins at `cargo install` time and gets any security updates at that point but no further unless they think to update
- being locked:
  - avoids "works on my machine" because everyone works from the same state
    - especially bad that there is no accessible record of what was built
  - reduces need for MSRV / minimum-publish age which have UX problems being used during `cargo install`

- https://github.com/rust-lang/cargo/issues/7169#issuecomment-1908436896 `--locked` is use case relevant
- https://github.com/rust-lang/cargo/issues/7169#issuecomment-1988592948 could and should we suggest `--locked` on error?

Josh: It feels we're talking about 2 different things here. One of them is how do we make cargo install reliably work for people. What if you want to stay up-to-date or handle security issues. We've said several times that we don't want cargo-install to be a general package manager. I don't think we want it to be a substitute for that and have mechanisms for version checking etc.

Josh: Should we have a single command that would go and update everything you have installed to the latest version?

Arlo: But does it pass `--locked` to each of the installs?

epage: There are issues around updating everything, there's knowing that updates are availability and critical updates. There's being able to reuse feature flags, migrating, installing manpages. I'm sympathetic to some of these, but I don't want to scope creep. I think that updating all might be sensible. It's true we don't help people with updates now. But for a lot of software now, a lot of them have a prebuilt binaries, there's matter of workflows of maintainers deploying software depending on that.

Josh: That's what I was thinking. If you're low-touch on your software releases, not shipping binaries etc. Then not using `--locked` is to those people's benefit. `cargo install` will always give you the latest version with the latest dependencies.

Josh: Some people are suggesting opting in to making "locked" the default for *their* crate. The higher-touch people might want to opt-into this. People go into great lengths to have a specific crate version to detect whether the user didn't use `--locked` and fail with an error message.
