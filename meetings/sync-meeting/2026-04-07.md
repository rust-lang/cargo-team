## min-publish-age

epage: deny vs fallback
- see https://github.com/rust-lang/rfcs/pull/3923#discussion_r3017984280

epage: This is the min-release-time proposal for Cargo. It's been getting updated slowly, but it's starting to mature. One thread to discuss now: if you set a min-publish-age of 10 days, that'll use the resolver fallback mode (that we use for the MSRV resolver). It affects the priority order of the package, it deprioritizes those below the publish age. You can work around the min publish age by updating a version requirement, bypass the min publish age and if someone injects something into the package, it'll be subject to min publish age and it'll be fine.

epage: But if the malicious actor publishes the package and yank all previous versions, we'll pick the package version that isn't yanked even though it's too new -- that's a hole in our security story. The alternative is to go with the deny mode. We treat things that are outside of min-publish-age as yank. And we'd have an exclude list in your configuration to use the package-id spec syntax and require a specific version of the package be specified.

epage: The downside is this only lives in config so if you're excluding something, if something tries to resolve it without the config around, it will reject it.

Arlo: Can we treat packages that are too new the same as yanked? Then you can still update, but you'd have to use --precise. 

epage: It's a very shallow method and I'd like to remove that. It doesn't handle the recursive situation. E.g. if I publish a new version of Clap and I want to force publish the version and it depends on e.g. clap-builder. So I'd have to update those as well.

Josh: When you say "hitting the recursive" situation, do you think that's particularly likely to come up in the case of a security update if it's needed?

epage: It depends, I don't have good data. But I think people won't only be doing it for security. Multiple main usecases: wait for the security scan window, another is rolling releases -- you slowly release out to everyone and people can set how old packages they want (risk/benefit). And e.g. for any release a Clap you'd need to update at least two packages.

Josh: For the security usecase, I'd expect "I have this one/set of closely related packages" -- that doesn't look like a big deal.

epage: For `--precise` you can only specify one package.

Josh: That's unfortunate. But there's a difference between needing 1-2 coordinated packages vs. needing one package and 12 newer packages it depends on. The former is potentially only for the security story, the latter is for more complicated things and we might postpone that.

Arlo: Any solution for this should handle the yanked version as well.

epage: I was going to proposal `resolver.yank = fallback`. So you could fall back to it but it wouldn't be a default.

Arlo: I feel you'd want to explicitly enable it, I wouldn't want it being default.

epage: I was thinking you would do that on the cargo command line. That you'd pass it the one time you need it.

Arlo: It feels scary to be able to have an option you can persist.

Josh: Sounds like a recipe for a lot of packages depending on yanked versions because people didn't know.

epage: Seems people are in favor of min-publish-age is deny instead of a fallback for the first release at least?

Eric: If it's deny-by-default and I want to update something beyond the age, would it be okay to just to set the env variable to fallback?

epage: If we support the fallback mode on release too. Right now the RFC only supports the fallback version.

Eric: When would the deny validation happen?

epage: This would be a part of the resolve just like yanked. Except if you have the package locked, we wouldn't let the version be available for resolving.

Weihang: Can we have a better way to hint people when we fallback? When we resolve a dependency it's a status message and 

epage: If people have a better way to do this, I'd love to be able to implemented.

Arlo: Would it make sense to just initially have the deny mode and an "off" mode? And just do an update?

epage: That could be done also. There are corner case between the resolver and update. Depending on what versions you're talking about, it can lock a version even if it's required to be updated. As a user I regularly hit these errors. So doing an allow and doing cargo update might still fail.

Jacob: That's a great summary. It fails sometimes and it's not entirely clear why.

epage: Questions: fallback by deny, exclude list? What do people think about the direction of the RFC.

Arlo: Trying to make it work as yank and having a way to get past it getting stuck.

epage: So no exclude list?

Arlo: No exclude list.

Weihang: If we want an exclude list, can we have a registry hook that cargo could provide for any result?

epage: This came up a few times, allowing the registry to customize the behavior.

Arlo: At my former work they replaced crates.io completely and did their security scanning without cargo knowing anything.

epage: Basically, treat this just like yank today?

Jacob: Whatever decision we make now, we can make it configurable in the future. Anything that's in deny form can be overridden by tuning the delay. None of this going to close the door as there's already an escape hatch.

epage: Arlo's suggestion was the minimum subset that doesn't have the yank problem that covers the usecase. We can always add more.

Eric: Sounds good, I agree with Arlo on this.

epage: Thanks everyone.

## Shorthand for `--manifest-path`

https://github.com/rust-lang/cargo/issues/16726

epage: I'm not seeing any problems with `-m` within cargo or conflict with other tools. Any concerns? Most people don't use `--manifest-path` but it will be frequent for cargo-script users.

Weihang: Do we want to add it after stabilizing cargo scripts?

epage: We could do it after but I think there's use regardless.

Arlo: I could see it both ways.

Josh: I think it cements the usecase of `m` means that it stands for "manifest path". It might not be the best option for people who haven't seen "manifest path" before. We could use `-s`

epage: I wouldn't want to make it specific to cargo script. It would be worthwhile to look at how other tools call flags like this. In general look at what flags and short flags they use. E.g. in cargo-tree `-i` means invert, but in a lot of places it means "interactive", or "input".

Josh: I wonder if we should add `-m` as "this makes sense with what we currently have now" and then consider adding another option as things change

epage: I want to at least look at what other tools call things to add to the document. We can have as many options as we want and we can choose which are visible in clap.

Josh: I would like to have a `cargo new --script` etc. but I think it's good to start with `-m`

Scott: Why not doing `--mp`? It's still shorter.

Arlo: The further we  get to the discussion I think we should just do `-m`

Josh: +1

Arlo: I do type `--manifest-path` semi regularly and I'd use it beyond cargo script.

Scott: +1. And `-m` seems like the least problematic option now.

https://github.com/rust-lang/cargo/issues/16531
- epage: ... somewhere someonme suggested `CARGO_LOG` like filters for controlling verbosity

epage: verbose means a lot of things to a lot of people and it can be too noisy. I don't know how noisy rustc verbose is. I'm concerned about verbose being so verbose it loses its value.

Scott: I can see `--verbose verbose` invoking `rustc --verbose`, but it feels strange to do it with `--verbose`

epage: I can see that. We're passing `--quiet` to tests e.g. But it would force a recompile because it's changing RUSTFLAGS.

Eric: I don't have a sense of how often rustc prints things in a verbose mode. It prints the linker stuff.

Jacob: On the linked issue jyn says it's just linker and occasionally very verbose type names.

Arlo: It doesn't seem to be doing much.

Weihang: We did, I think the issue was accepted.

If we make `--verbose` cause a recompile it would limit its use. But if we can always record it and just not show it, that would be great.
