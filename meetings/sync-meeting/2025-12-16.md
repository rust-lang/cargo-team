## (backlog) Rerun-if-changed without disabling other heuristics as a side-effect

https://github.com/rust-lang/cargo/issues/4587

Eric: The default behaviour of cargo is to check any file in the package if it's change. Once you start using rerun-if-changed, it disables the default heuristic and only does what you tell it to do. kornelski's request is to not disable the heuristic but also add the rerun rules.

Josh: I wanted this several times as well: "please also rerun this thing if changed" but I don't want to duplicate Cargo's logic

Josh: The proposed syntax for `+=` seems sensible.

Jacob: There's a related request: "I'm a utility library and I don't know if the default is being used. If it is, I don't want to change anything, but if it is used, here are the things I care about". It's unclear if `+=` would work there.

Josh: Another option would be to keep the current mechanism and add the way of saying "add all the defaults". To say "rerun-if-changed-defaults" or similar, and also add explicit rules.

Weihang: There's another issue where we want to be able to disable all the heuristic and let people specify the changes they want to renun. If we add the explicit default heuristic, it'd encourage people to use it

Eric: For things like package config you don't want to use the default. You don't want people to override that.

Josh: That makes sense, 

Eric: I wonder if we want to add "rerun-if-changed=.".

Josh: Yes.

Eric: Maybe we could change it over the edition and remove the default and make it an error if the build scirpt doesn't specify it.

Jacob: We could start with showing a warning.

Eric: The default is almost never what you want. If you changed a random file in your tree 99% of the time build script doesn't care. But it will be run.

Arlo: I really like the suggestion of adding the warning, showing how to add the old behaviour but telling them they likely don't want it.

Scott: 

Arlo: Ideally, we'd magically track what you changed in your source tree but i don't know if that's feasible

Josh: Long-term this is one of the benefits of the sandbox mechanism. People would like to track everything you've accessed and used and treat that as the list of things you need to rebuild.

Josh: I love the idea of changing this over edition to make it explicit to say what you want. And you'd presumably only specify one of those (don't rebuild if . changed or do) if you use rerun-if-change

Arlo: If you don't specify anything, it wouldn't do anything?

Eric: If we make a change across the edition, we want to make sure people undertand what the change is and make sure they update it. We don't want a silent behaviour. So either explicitly say something and if you don't it's an error or if you don't specify it, it's the current behaviour. With other edition changes in your source code, if you don't do something it normally doesn't compile. But for edition changes like this, it's more tricky.
