## Splitting `dev` and `debug` profiles

epage: have a rough plan but ran into some issues
- `build.profile = "debug"` would make the transition smooth, but what about `cargo test` and `cargo bench` with their custom profiles?
- Should `debug` inherit `dev` or be a root?
- https://github.com/rust-lang/cargo/issues/15931

ed: One idea is to not move "dev" out of the "debug" directory. 
Concerns: build profile config field, so that people can set what behavior they want. Ran into some issues.

josh: There's something in common between this config field... Today, can I make release the default? Answer today is to set the debug profile into a release profile. Instead, we could have a default profile config option? That would solve both of these problems.

ed: That's what this build profile field does. It uses this field if you don't specify on the CLI.

josh: May want a command-line option to switch back?

ed: Considering adding flags (like `cargo install --dev` (or `--debug`?)).

ed: A problem is that test/bench has their own profile. We don't document test and bench profile. Only shown in the finished message. Could add things like an install profile field. Could add different options like profile.test.inherits to control how these individual things inherit.

josh: It would be helpful to align the profiles so that you don't get rebuilds when switching from a build and test.

ed: Could have test inherit from the default build profile (instead of dev). Don't like it being dynamic, though.

josh: Test being a separate profile seems sketchy.

ed: Test/bench profile motivation is uncertain.

josh: Use `test --release` because I don't want to rebuild after building in release. Setting a profile for default, that could apply to test.

ed: So keep `test`, and if you set the default it would apply to that.

arlo: Wouldn't it be a breaking change to change it.

ed: I mean the fallback scheme for `cargo test` and `cargo bench`.

josh: Weird idea: What about a configuration for what `--release` does, and then it'd also be the default for bench if set?

ed: Would like to know more about the use cases.

ed: The other problem two different schemes for built-in, there are the root profiles, and then test/bench inherit. Should debug inherit from dev? Or be a distinct root profile.

scott: What is the planned overlap.

ed: Codegen units, incremental maybe. Considering whether it is an "addition" to the other profile, or is it its own distinct workflow. If users change the base, they can change the inheritence. Leaning towards debug from dev.

arlo: Would prefer to inherit. Seems like there should be enough overlap. May be challenging to have to set something in three different profiles to make a change.

josh: Would also like to inherit. Historically had "dev" profile for debugging, and profile.dev settings are intended to apply, and if debug inherits from dev, then they get the settings they have already set in `.dev`.

ed: Minus the things that debug profile overrides.

ed: Was expecting two-stage migration. Make the split, and then change the default.

josh: Would expect the things that debug overrides from dev would be limited.

ed: opt-level is one that would be different. debug's opt-level would override dev's opt-level. dev's settings are specifically to make things faster.

jacob: Should this be coordinated around edition changes? Not tied to an edition, but just so that people can consider that at the same time. Maybe it would be easier for people to make changes that way.

eric: Would note that we changed how profiles worked in the past, and it seemed to go through ok.

josh: Looking forward. Defaults are important and it's good that we spend a lot of time considering them.
