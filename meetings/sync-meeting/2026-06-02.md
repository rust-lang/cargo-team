## (backlog) cargo should avoid releasing jobserver tokens when it's going to need a new one

https://github.com/rust-lang/cargo/issues/7786

(Continue from [previous week](https://github.com/rust-lang/cargo-team/blob/main/meetings/sync-meeting/2026-05-05.md#backlog-cargo-should-avoid-releasing-jobserver-tokens-when-its-going-to-need-a-new-one))

Eric: I took a closer look at this. During the last meeting we were thinking about closing this. One of the main concern was that if cargo grabs tokens more aggressively, it would starve other things in the build system. And that's the whole point of what @glandium wants to do. Cargo's getting starved. Rustc build units tend to be more heavier than C units.

Josh: I chimed it with that concern. Performance issues aside, my concern is I saw a number of tools trying to be creative with the jobserver protocol and inevitably there's a deadlock, live lock, starvation etc. when they're holding onto tokens. It always seems to go horribly wrong. There's a reason the protocol is so simple.

Eric: Weihang, you weren't here. Do you have any opinions?

Weihang: That's how jobserver works, right?

Eric: The jobserver protocol isn't very well defined. It doesn't say you can't hang onto a token opportunistically. That's what this would be doing.

Eric: Does anyone know whether glandium still work with Mozilla?

Josh: I think so, but I'm not sure. Looking.

Eric: I assume Mozilla is still using make

Ross: I see commits to firefox on their profile recently

Josh: It's reasonably likely this would ultimately produce someone's incensed blog post saying Rust is selfish in its use of a build system. I don't want that hitting Phoronix

Scott: I don't know if the effort put into finding a good heuristic is worth it given all the trouble. The maintenance burden would be extremely high

Arlo: Any change we make here would break someone

Eric: Mark mentioned this could be an optional flag

Josh: It would be vaguely helpful to have any numbers here. If someone could do a quick prototype demonstrating the speed up would help here. I also wonder if there's a helpful tool that could build around this. Cargo doesn't need to be involved. It would be easy to have a CLI wrapper that would run the command undernaeth with a modified pool and would demonstrate the point.

Arlo: I like that idea

Scott: +1

Eric: I envisioned Cargo would only retain tokens as long as it had work to do. I assume they're using large build servers.

Josh: On a sufficiently large projects I can max out 90+ cores. The usual pattern I've seen with 100+ crate projects is building the few crates everything needs, then fan out until it runs into another bottleneck. But it does run shockingly well.

Eric: I can ask glandium if they're still around and care. Leaning towards closing unless we get significant evidence on whether this makes a big difference.

Arlo: Would be useful to get an update from them. E.g. if they found a work around.
