AFAIK, the primary one is that not a 100% of things are solved by changing directory. Not sure to what extent this is worrying. We don't describe it as "search for everything as if you started there" vs. "just build from there".

Weihang: IIRC, the major blocker is rustup?

Josh: Things that are read by rustup before we start we can't possibly respect. rustup will read the toolchain file wherever cargo is invoked. Then it will invoke cargo, and cargo will look at the -C option. ??

SCott: We should document it well. Does rustup have a way of knowing if it's overridden?

Josh: We could do the next best thing, check for obvious things. But rust-toolchain is already very hacky.

Weihang: If we do that, is that a blocker for future rustup features?

Ed: This should just be a best-effort warning that we could delete later.

Scott: We could just warn that rustup is running under an override.

Ed: Generally we had a strict policy about avoiding warnings that they should only be emitted when the user can silence them. This one has a high false positive rate and no way of silencing them.

Josh: There's one other thing we could do. If someone passes the -C option, it's likely they will do it early on the command line. Wondering if we could say this can only be passed as the first argument. That would simplify the parsing enough for us to ask rustup to handle it.

Ed: We would still need to implement this if someone uses cargo without rustup. I'm hesitant about position-sensitive arguments.
