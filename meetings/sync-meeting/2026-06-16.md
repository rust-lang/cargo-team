## (regression) Cargo will lose inter-process file locking on Solaris on with 1.98-nightly

https://github.com/rust-lang/cargo/issues/17084

What do we want to do here?

Eric: Weihang, can we just revert the thing we removed from cargo?

Weihang: Yes, we can just revert to whatever we did. The process-level one should be fine, right? We don't care about file handles and stuff. Cargo is a process-level process

Eric: It's never been a problem before and cargo's use fits within the limits

Weihang: Then probably we should just revert it. But there are more places now. Ross added fine-grained file locking now.

Eric: I was thinking just reverting the Solaris file locking side

Weihang: There's the filesystem API and our own flock wrapper.

Arlo: Did we make this change in Cargo or stdlib?

Josh: Standard library added file lock handling. We said we could use this in place of our own hand-rolled file lock handling. Then it added that to Solaris and later reverted because it didn't match what the other platforms did semantically.

Josh: We'd either have to do something custom for Solaris, custom for everyone or decide that Solaris doesn't need file locking

Weihang: That's already what we had before the other Solaris folks added. So maybe we can not add it back and see if people who care come to us.

Josh: Is there any chance the Illumos folks either fixed it or might fix it?

Weihang: I remember someone (Josh Stone maybe?) saying Illumos supports the standard POSIX file locking and Solaris doesn't.

Eric: Have we heard from any of the Solaris maintainers?

Weihang: No. The bad Solaris support was added by me and that got reverted. I pinged the Oracle Solaris maintainer but they didn't reply

Jacob: If you're not tier-1 and you don't show up when we ping you, you either get broken or removed.

Josh: We'd need to do more poking before we follow through with that. But Solaris is tier-2 with host tools right now. I wonder if we could make it tier-2 without host tools.

Arlo: Right. Maybe proposing that might get the maintainer's attention.

Josh: It's reasonable to ask. People would still be able to cross-compile to it

Arlo: Would this require stdlib changes for Illumos?

Josh: Yes. They're two separate targets though they share most of the code. If we can get it fixed in Illumos or figure out that it already does. I think 90% support for Illumos is handled by the Oxide folks. I expect them to be more supportive

Weihang: I found the source code and it lists as it's supported

Arlo: So it's already there. We wouldn't need any stdlib changes?

Josh: https://github.com/rust-lang/rust/issues/146312 this confirms that Solaris and Illumos differ here

Eric: Let's try pinging the maintainers again. If they don't reply I propose we don't do anything now.

Josh: Depends on how much development you're doing on Solaris.

Tomas: Do we need to highlight this somewhere? Blog post, release notes etc.? 

Eric: There's a proposed release note: https://github.com/rust-lang/rust/issues/157510. But it needs the description filled

## (backlog) Don't use incremental compilation for build scripts

https://github.com/rust-lang/cargo/issues/8545

Previous decision is that the performance impact either way is probably not substantial. (But we don't have data on that?)

Release builds do not use incremental.

Eric: There were previous discussions about this from Alex. The performance hit from incremental is small, but performance hit of not using incremental is small -- both because build scripts are usually small. So it could go either way. Also, people normally aren't doing a lot of iteration on their build scripts. Of course when you are modifying it, you want the iteration fast.

Arlo: Was there also a request to run buildscripts in release always?

Josh: There's a lot of discussion about whether you should compile syn etc. in release/debug mode etc.

Arlo: Seemed relevant in how people wanted to control how their build-time dependencies are compiled

Josh: We talked about the hint min-opt-level. That was less about proc macro parsing and more about building perfect hash functions that can be large etc.

Arlo: I was thinking about something like hint incremental here

Josh: When we're doing incremental builds, we do that for the current crate we're working on. Do we pass it to the dependencies?

Eric: No

Josh: So this would only apply to the current crate

Eric: If we turn it off, if somebody wants it on, they can just update their profile to turn it on

Jacob: It was stuck open because it isn't need that much so it gets stuck open

Eric: How about we switch it to needs info, ask for performance numbers for a typical project. What's the perf hit

Weihang: I feel it won't affect it that much.

Josh: Probably insignificant in both ways, but it'd be good to have the numbers to tell us. E.g. this saves x% on build vs. time on doing incremental development. Numbers for a tiny/massive build script, incremental/full cost on these, that would be sufficient

Arlo: If someone spent some time to do this research and it showed that it's really beneficial we could reopen it

Eric: We can put it in our list of queue of things to investigate later. And in a few months when someone gets to the queue we could close it.
