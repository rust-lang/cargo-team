## host/target profile reuse

- epage: https://users.rust-lang.org/t/why-are-builds-of-my-crates-test-not-consistent-cargo-build-vs-cargo-test-vs-vscode-test-explorer/139622/4?u=epage
- rebuilds between packages because a host/target sometimes get shared and sometimes not

epage: Eric I think you said in the past that we did this, but there are pitfall with it. I saw one on users ^. The person ran into a deep dependency that's either shared or not with the host target and that's causing extra rebuilds in dependency tree. How do we find that these are shared and do we want to continue down this path?

Eric: It's the trade-off of longer compilet times to complexity. My first thought: try to answer the question of how bad would compile times be hit by not sharing anything. If we can answer that clearly, we'll have more solid foundation to make a decision.

epage: In this case is hurting compile times. But if the person did a workspace-wide feature resolution it wouldn't hurt their compile times. Last this came up was when Liquid changed some build-specific settings where there was less sharing. The whole thing there was a bit of a wash.

Eric: Was that about changing the debug setting?

epage: Probably. Sounds like there's too many real-world usecases to determine how much this is hurting or helping.

Josh: Is there a consistent answer for release vs. debug? For the release I'd likely run with "target packages built with O3 and host packages with O0". But for debug build they'd likely both be O0.

epage: Aren't build-scripts still built with the current build profile?

Eric: Release builds don't share anything.

epage: We effectively have a build override in place.

Josh: It was a common advice and we made it the default at some point.

Josh: We may want to think about those scenarios differently and that might help us avoid the "some are win and some are loss" scenarios. In the debug case you care more about the compile time. In the release mode you're trying to build a binary that runs as fast as possible. So the compile times may be less problematic.

epage: Some workflows we care about helping and some we don't. The fact that it helps some poeple and hurts other people still impact the dev profile.

Josh: So there are both dev and release cases that have both?

epage: This is about the fact that there's sharing that hurts build-time performance hurts at least some users. If we already have default build overrides and no symbols, I wonder about O1. That should be fast to optimize and help runtime faster. So there might be an improvement there instead of dropping sharing.

Josh: If O1 is effectively Ofast, then dev profile should be using O1 for build dependencies and target packages and release should be using O1 for build dependencies but continuing to use O3 for target.

epage: Sounds like this is an unknowns where it's hard to act.

epage: I think the feature is changing where the dependencies are being used. If the feature's causing whether the dependency is only going to be used on the host or target, that's going to have a different profile setting.

epage: Probably not worth it at this point. I remembered Eric you had some reticense in the past so I wanted to bring it up.

epage: I've noticed for Cargo we have flate2 as a build dependency. So that's where we get sharing as a benefit.

## Make target dir self-ignoring

https://github.com/rust-lang/cargo/issues/15061

Whenever cargo creates the target directory, it should also create a file target/.gitignore with the content * to ensure the directory ignores itself.

- Dongpo: The original motivation is that `a top-level .gitignore file checked into version control can often be avoided`. However, I don't think this applies in this case. In most situations, you still need your top-level .gitignore file because you typically won't have only `target` as the sole content for it. It seems that [this](https://github.com/rust-lang/cargo/issues/11548#issuecomment-2735134860) is a more reasonable and valuable motivation to implement it.

epage: previously discussed at https://github.com/rust-lang/cargo-team/blob/main/meetings/sync-meeting/2025-12-02.md
- https://github.com/rust-lang/cargo/issues/6357#issuecomment-3603101763

dongpo: I came across this PR. We didn't accept the issue the PR is for. But this issue split to another proposal that suggests we do this but also remove the `target` item from the top-level `.gitignore` file. I wanted to check what your thoughts are.

dongpo: The original proposal was to remove the top-level .gitignore entirely. I don't think that motivation makes sense. But there's a motivetion where you have an older project you want to introduce Rust into and you run `cargo new` within the directory, it already has git and it so it doesn't generate the .gitignore file. And tools like `jj` track these ignored files and you have to remove them manually.

epage: We have an issue about cargo new always writing out gitignore. There's some hesitance from people on the team about the self-ignoring gitignores. For me, this is vcs-specific. And if we're always writing this in the target directory, we don't know which VCS we use so we have to write them out for all of them. And now we have to do it for the build-dir too.

Arlo: I had similar thoughts about this. I've also tried to look at what other package managers are doing. And as far as I can tell, no one is doing this gitignore in the generated directory that I could find.

Josh: We already generate a .gitignore at the top level. So generating one inside it feels potentially overriding a preference someone might already have.

Arlo: We only generate it in cargo-init or cargo-new

epage: And we only do it for a new repo, not when the repo already has VCS in. Should anyone be doing anything inside the target directory they shouldn't already have ignored?

Josh: ??

epage: If we put this in the target directory, people will start relying on it and we're stuck supporting this

Josh: It seems there are 2 issues here. (1) do we stick it in the target directory and (2) do we stop generating the top-level gitignore? That would surprise people.

epage: So even if we had the self-ignoring target directory you'd want to have the top-level one?

Josh: I don't think we should stop generating the top-level .gitignore. I think we should generate it for existing repositories too. I'd do that rather than stuff something in the target directories.

dongpo: If we run cargo new within an existing directory, we don't do anything. But for cargo-init if we try run it within a repo with a .gitignore file, we do add the target dir in there.

Josh: The question is more about: is this .gitignore actively harfmful? If you're ignoring something you don't want to ignore are that's an issue. You shouldn't have a directory named "target" in your target.
