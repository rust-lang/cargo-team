## Crate publish quarantine

weihang: Jess Izen `@jlizen` would love to briefly discuss about the relationship between min-publish-age and a prospective quarantine in crates.io. For example,

* how it relates to SLA on human curation for flagged crates
* implications for multi-workspace publish

Jess: I'm starting a residency with the Rust Foundation. We've got good heuristic-based system that flagged last week's attack, but it needs a human in the loop. We could react -- to yank published crates out. The other option is to flag something sketchy and manually review that. I'm scared about doing it reactively. I don't like the idea of there being a security incident if we don't get to it in type. The PyPI folks have a long review queue of suspicious reviews, I expect the queue to grow here.

Ed: Quarantine means a lot of things to a lot of different people. Sounds like what you're saying is: it's only going to get quarantined only if it's suspicious.

Jess: Yes.

Ed: Depending on the false positive rate for suspicious packages, we can allow the tooling be a bit jankier.

Ed: With min-publish-age and changes to default, is this the most important thing to be done?

Jess: min-publish-age would have solved this attack but I worry on the long-term stress of the security folks

Josh: Sounds like you're saying that min-publish-age is a configurable mechanism the user sets and if we set a default, most people will get it. But the failure mode of the default mode is "we run out of time and it's available" vs. the mechanims you propose is "we run out of time and miss an SLA". 

Jess: I'm not trying to impose a blanket quarantine age. Everything that would go into the manual queue would be stuff that gets flagged.

Josh: May need to make everything give the impression of being flagged, and then have things that pass the heuristic scan get a shorter quarantine, so that we don't provide an immediate signal to malware of whether they pass the heuristic.

Josh: Our min-publish-age assumption is that we'd ship a default in Cargo. But we could also get the default from the repository we fetch the data from. Fetch a recommended min-publish-age from crates.io and periodically re-fetch it.

Jess: That's a great idea. I'd be interested in pitching both ideas

Arlo: If we start diverting things into this quarantine system, it'll impact how cargo-publish currently works. You also talked about making it only visible into the author. If we end up splitting the index etc. that would cause issues with signing

Jess: It's matching what Python uses. They have a reactive quarantine right now, but they're adding a proactive quarantine.

Jacob: Let's talk about the implementation

Jess: I'd like to have a temperature check. I suggest we add a behaviour that by default attaches credentials for fetches that are associated for publish and crates.io allows you to use your crates even if they're in quarantine. And that if your crate is in quarantine, all your crates are in quarantine. Does that roughly sound reasonable?

Jacob: The idea is there'd be a new endpoint that looks like an index that (when authenticated) only the user can see and it'll show their quarantined crates?

Jess: Yes. And it moves most of the logic to crates.io

Josh: Another aspect to think about: how do these two things interact (min-publish-age -- does it start by the time you enter the queue, or exit the queue).

Jess: Good question, we should discuss this in the RFC

Josh: Agreed, the RFC should answer this question

Ed: There's a talk of a "staging ground" quarantine. Do those situations need a sandbox to publish into and then publish the whole sandbox?

Ed: Is it only on publish we'd use the credentials to read the index?

Jess: I'd prefer it to not be a default behavior on all fetches.

Ed: If it's not for all fetches, a later fetch will then overwrite that and lose access to it. And sometimes you need to release packages in a group. Sometimes you need to have a few separate releases in the group.

Ed: To me the highest priority to this attack is we store credentials in plaintext. If we're talking about multiple across cargo invocations, we wouldn't be able to do this without 

Jess: So that specific design won't work, but maybe something more complex could. Sounds like I'd need to deepen my understanding of the identity sessions.

Arlo: Agreed with getting the plaintext credentials out of there. It sounded Jacob was saying this would be a crates.io API call not related to the index. That's potentially feasible, but it would not be exposing another index-like API. That would be a separate thing -- an overlay to be designed. And Jess was thinking ??

Jess: I was thinking the latter.

Arlo: It makes signing practiaclly impossible. The mirrors need to be able to serve signed content without talking to crates.io interactively.

If we find something likely has malware, we could immediately say: "anyone who has access to that, we know what credentials they have" and we anything uploading from those credentials could immediately be quarantined too.
