## (backlog) `cargo build` doesn't update binary timestamp

https://github.com/rust-lang/cargo/issues/8649

Timestamp changes to `Cargo.toml` can cause complications with other build systems.

Josh: Can we reliably tell the difference between nothing important changed, and nothing changed. I think it would make sense for the "something changed, but don't need a rebuild" to update the mtime. Slight downside if people rely on that, it could retrigger a rebuild. 

eric: what is meant by "important"?

josh: If you touch `Cargo.toml` that its timestamp is updated, and then build, cargo could see the timestamp is updated, but the contents don't change, so it doesn't reubild the binary. So `make` will invoke cargo every time, since it doesn't get things updated.  Differentiate between a timestmap change (with no acutall changes) and no timestamp changes (because we don't want to touch the timestmaps of the output on every build).

arlo: Personally don't like this, would like the build ssystem to touch the timestamps of the files as needed.

josh: Seems reasonable, if you are dependent on mtimes, you can update them yourself. But if cargo can check it, then it could help, but if not then we shouldn't adapt to that.

weihang: Recall rustc has a change with incremental, if rustc found there is no change, it won't change the outupt file, which broken cargo. Don't recall if we said anything, but they did change it so that it touches the file.

josh: gratuitous mtime propagation seems overkill. 

weihang: rustc didn't change, cargo applied a fix:
- https://github.com/rust-lang/rust/issues/148948
- https://github.com/rust-lang/cargo/pull/16262

arlo: Feels better the do-nothing.

josh: Yea, adding a touch to the output step in your build system seems like the reasonable thing.

weihang: Yea, could link to rustc. 

eric: confused, it seems like we added mtime propagation for rustc rmeta generation. Why not also add that for `Cargo.toml`.

eric: 

josh: Seems fine to re-invoke rustc since it has incremental to not do as much work.

eric: Just had a thought it will be much worse when we switch to content-based hashing.

Eric will try to circle back on this to see how complex of a change it would be. Eric's preference is if it is relatively easy to support, then that sounds reasonable. But if it requires a lot of changes to cargo, then probably not interested.
