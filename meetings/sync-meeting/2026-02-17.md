## (backlog) Cyclic dev-dependencies can cause confusing errors

https://github.com/rust-lang/cargo/issues/6765

Eric: This is the problem where a cyclical dependency causes two distinct objects with the same version. You're kind of mixing two different crates together. Recently they added extra msg to the compiler to help the user a little bit. Otherwise I don't know if there's anything else we can do. We could improve the error message.

Jacob: The improved error message isn't really helping much in this case.

Ed: I assume one of them is with a test flag, and the other isn't. Maybe we could augment the error message with information on which of the versions uses the test flag.

Eric: Two scenarios. One is with unit tests, where this would work; the other is with integration tests, where it won't. It's also trying to mix and match types. That works sometimes, but it might not if you're pulling types from both crates as duplicates.

Scott: Could we detect this statically, maybe lint against it?

Ed: Its' a combination of compiler and cargo. One of the ways to get to this is people trying to activate a feature on themselves in tests. So it's if you have a dependency on yourself and you get this compiler error, you're hitting this.

Eric: There's a scenario where this works. Both the compiler and cargo don't have enough information to detect this.

Scott: It would be great if rustc could say "hey, you may know more about this" and Cargo could say "yes" and provide more information

Ed: Similar to pub/priv dependencies but more scalable.

Arlo: I think there are other places where cargo runs under the compiler and can use that to output extra information.

Scott: This is more about "rustc" saying "I'm running in a build tool, you may have more information to look at"

Eric: I think this will be a significant R&D project to handle a relatively rare problem. We could have someone do the work or just document it.

Ed: I'd be fine closing it.

Arlo: There are better areas we could invest our time in to improve user experience.

Ed: The maintenance of this -- around the brittleness of this -- would outweight the benefits.

Josh: Detecting cycles might be a worthy effort, doing more might not be.

Arlo: Could we have an off-by-default lint that could detect this?

Jacob: Or on-by-default lint saying you have a cycle and this could cause a lot of problems. If you need it, silence the lint.

Josh: A lint sounds like a good idea because then you could use the lint system to disable it.

Arlo: That sounds like less work but still a fair amount. Not sure it's worth it.

Scott: Detecting cycles might be hard.

Jacob: There's already a dependency cycle at the end of feature resolution. We could copy that in.

Scott: There's extra information that might need to go in the resolver, but we don't have anything there right now.. So copying/pasting might be our best bet.

Arlo: What do you think? Do we discuss the possibility of a lint and keep it open?

Eric: That seems fine.

Scott: you can label it A-new-lint and put what we want there.

Eric: I don't know what I want here though.

Ed: A new warn-by-default lint would cause false positives and this could have performance impact. We don't cache the lint.

Scott: That's why suggested it being off-by-default

Ed: But then it won't provide value to users.

Josh: I'd suggest just "you have a cycle, that can cause problem" not saying more specifically where the issue was. Ed, I was wondering what's the reason for having cyclic scenarios in the first place?

Ed: We actually support this so that some packages with cyclic dependencies could be published (e.g. clap).

Eric: Cargo itself used to use for testing.
