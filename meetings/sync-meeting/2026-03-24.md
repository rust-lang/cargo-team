## Vibe check on async

https://github.com/rust-lang/cargo/pull/16745

Arlo: Do people think it's a good idea? Are we ready to do it if performance is good enough? Thoughts? I think it's pretty much ready for review.

Ed: Is the motivation mostly code cleanup? Whats' driving it?

Arlo: Initially, it was a cleanup effort. For the Merkle tree signed registry extensions, it's painful to add ability to download things in parallel. I thought building it on top of async is easier. Also, I hoped to get improved performance. It seems a bit better but the benchmarks are not fully conclusive yet. It also separates our backend from using cURL directly. So we could add other backends in the future.

Ed: Could you document that in the PR description?

Arlo: Good call, thank you.

Josh: Thank you for worknig on it. This is a good idea overall. Cargo is a long-standing synchronous codebase and introducing async into it, be careful. It's easy to end up blocking code on an async thread. Try using debugging tools with the async runtime to help detect that. Also, people may be surprised if Cargo suddenly uses all the threads in their system -- pay attention to things like `-j` etc.

Arlo: The async runtime I'm using is the futures executor that only runs on the current thread. It doesnt't start additional threads yet.

Ed: Can you please also specify the executor on the PR too? And mention your motivations are. For the historical record.

Jacob: I don't want someone in the future to say "cargo doesn't want to use Tokio" and citing this PR.

Arlo: Good callout. I tried to make this witwh as minimal dependencies as possible.

Josh: It won't be hard to port this to smol which also provides `block_on` and that will be really hard to port to Tokio. Tokio really doesn't want you to call `block_on` from any thread that's currently running an executor.

Arlo: The executor I'm running has the same constraints.

Josh: In that case it may be easier to make that work.

Arlo: We're quickly starting/stopping so if block_on is expensive, that could be a problem.

Ed: We had our own definition of waht blocking was (network operations), but the expectations around that start to change when even things like file operations start being blocking. How viable is it going to be going into sources that didn't need to be async before.

Arlo: I don't think it needs to spread now. I don't think using blocking IO in an asnync context is not a problem here. We're using async here for networking operations. The majority of our time is in networking operations.

Ed: This is more than just async IO. Just the loading and initialization of the manifest in the source can also be expensive. We should document this for anyone in the future.

Arlo: The executor I'm using doesn't even have async io for files.

Josh: Does it have some sort of epoll loop for sockets?

Arlo: No. Currently it's still using cURL's multi interface. As soon as we start the HTTP request we start one thread that manages cURL for you.

Josh: My gut reaction is that baking the assumption that async is only for X (e.g. network) and nothing else is probably something that'll create a lot of technical debt. People will want to use async inside of cargo and not realize it'll be just for network. If we start using something other than cURL, it may make assumption on the runtime that aren't currently there. How big an overhaul would be to just throw something like Tokio in? Whether to use, or to just run `tokio-console`.

Arlo: That could be an interesting experiment.

Ed: Does the current PR serve as a stepping stone to do this work in the future? Or would we have to scratch it and do something else if we e.g. switch to smol or tokio?

Arlo: The PR's already getting big.

Weihang: There's still some libcargo users, if we want to put some executer in our lib code, we need to make users aware of that. Nested executors can cause trouble (e.g. panic).

Josh: With Tokio you can ask if there is a tokio executor on the thread already.

Jacob: That sounds like a really useful piece of documentation. It would be great to figure out how this gets hooked into AIs so those can follow it when generating code.

## Clean up crate type names to fix dylib vs staticlib confusion

https://github.com/rust-lang/rust/issues/153863

eric: Thoughts on impacts to tooling that reads the crate-type?

(open discussion)

eric: I did github searching to see how many tools are using this. There's a large number using cargo metadata type looking at `if crate_type == "rdylib"` etc. All those tools would have to be updated to support it. Are we okay with that?

Josh: Are these tools generic or part of specific build systems?

eric: They're like build tools.

Josh: So reasonably generic, not just in a few projects' specific build systems.

eric: no. There's e.g. cargo-swift, cargo-gcc-rs.

Josh: something like cargo-gcc-rs I'd expect to be able to follow suite with us. But something like cargo-swift might not

Ed: We could allow them as aliases for the current values. We could accept them but output only the new names.

Arlo: I was going to suggest that too.

Jacob: That could also be an edition thing.

Ed: Or it could be a new message format version. But it might not feel worth doing for just this small change. And therefore risk leaving it like this forever.

Arlo: What's the full impact of changing this?

Ed: Compiler messages, metadata.

Weihang: All the JSON messages.

Arlo: I'd like to see that covered in the issue

eric: I can write that down

Josh: It seems there's never going to be a good time to do this other than some format versioning. If we keep emitting the new names and treat new ones as aliases, we're introducing different compatibility headaches. Tools will have to look up the old name even when using the new names.

Ed: This isn't the only place. In previous cases (the debug symbols), we accidentally broke things by outputting names instead of the numeric values. There are areas for improving our JSON output. Might be interesting to track these and have notes where we use the new name if we add new messages. Having a more running document on these might make sense.

eric: Josh, we do have documentation that says we're allowed to add variants to our json output. In this case, the cargo-metadata crate have an "Other" enum variant for crate types. If you add anything there, cargo will pass it to rustc will pass it as is and cargo-metadata will serialize it as is. But none of the tools handle this.

Josh: So a new version of a crate that uses a new version of metadata could check for this. Actually, cargo-metadata the tool could emit both string values. cargo-metadata could parse both of the values and send them to the same enum variant so all existing code continues to work. So it could break code that parses the raw output. But people who are using our crate will get the abstraction layer that could rename the value in a breaking change future of that crate.

Jacob: Yes, and we should document our plan. And state that tools should be able to read both values and treat them identically. And a rollout should include a change to cargo metadata where it's treating them identically.

Josh: eric, when you read through the instances in the ecosystem, were most of them using cargo-metadata or parsing the data directly?

eric: I only looked for things using cargo-metadata itself. But there are other languages (like Python) that might be parsing this so just cargo-metadata won't solve everything. I'm still okay moving forward with it, but less enthusiastic now.

Ed: I know one person who cares very much about the size of their dependencies who chooses to not use cargo-metadata.

Josh: I don't think we should treat that as the normal case.

eric: People also handroll their own message parser because cargo-metadata doesn't handle the recursive depth parser. Cargo rolls its own, bootstrap also handles its own.

eric: I'll try to write something up. I'll redo my survey of all the places where it shows up.
