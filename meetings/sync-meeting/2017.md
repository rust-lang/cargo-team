## 2017-05-25 Public/Private Dependencies

- [rust-lang/rfcs#1977](https://github.com/rust-lang/rfcs/pull/1977)

Living the dream:

- You’ll never dread making updating a dependency (to a new minor version)
    - There’s a GSoC project working on a tool to verify minor version bumps indeed don’t change their public API!


    // Crate shared
    pub struct Shared<T> { .. }


    // Crate foo
    extern crate shared;

    // public API, in which a type from crate `shared` appears
    // THEREFORE: `shared` is a public dep
    pub fn make_shared_i32() -> Shared<i32> { .. }


    // Crate bar
    extern crate shared;

    // public API, in which a type from crate `shared` appears
    // THEREFORE: `shared` is a public dep
    pub fn use_shared<T>(shared: Shared<T>) { ... }


    // Crate end_user
    extern crate foo;
    extern crate bar;

    fn main() {
     // bar::use_shared(foo::a())
    }

Another subtler example: https://github.com/rust-lang/rust/issues/22750


- A depends on:
    - B 1.0 which publicly depends on C ^1.0
    - D 1.0, which has no dependencies
- When A is initially built, it resolves to B 1.0 and C 1.1.
    - Because C's APIs are available to A via re-exports in B, A effectively depends on C 1.1 now, even though B only claims to depend on C ^1.0
    - In particular, the code in A might depend on APIs only available in C 1.1
    - However, if A is a library, we don't check in any lockfile for it, so this information is lost.
- Now we change A to depend on D 1.1, which adds a dependency on C =1.0
    - A fresh copy of A, when built, will now resolve the crate graph to B 1.0, D 1.1, C 1.0
    - But now A may suddenly fail to compile, because it was implicitly depending on C 1.1 features via B.
- If A does not depend on features from 1.1, there are two possible correct resolutions:
    - A gets C 1.1, and D gets C 1.0
    - A and D both get C 1.0
- If A *does* depend on features from 1.1, there is only one possible correct resolution:
    - A gets C 1.1, and D gets C 1.0

Is there a problem here even without public/private dependencies???

    - B 1.0 which ~~publicly~~ depends on C ^1.0
    - B author runs `cargo update` and gets C 1.1, starts using features added in C 1.1, doesn’t update Cargo.toml but effectively depends on C 1.1
    - ????

If versions are incorrect today, which they probably are, why are we going to try to prevent this tomorrow?
