## cargo update downgrades locked versions that are newer than min-publish-age

- https://github.com/rust-lang/cargo/issues/17642

Weihang: Even after you allowed some packages to bypass min-publish-age, `cargo update` would not pin that package version again, and would still change to min-publish-age respected versions. The current workaround is passing `CARGO_RESOLVER_INCOMPATIBLE_PUBLISH_AGE=allow` with the same `cargo update --precise` again.

Weihang: we might need to figure out a general pinning/allowlist solution, if we are going to have more resolver policies.

Ed: the goalwith the min publish age RFC was the lockfile to be allow list. When we do an cargo update, yank can't downgrade the version. If your version requirement allows it, we downgrade, if it doesn't we error. I feel we should make it so it works fine. If something's already in a lockfile, it should at least be a candidate if not preferred. When you run cargo updade, what do we want to do with downgrading?

Josh: The RFC said once the versions are in Cargo.lock, they'll be kept

Ed: We overlooked the update

Josh: I could see cargo update being stateless and ignoring `Cargo.lock`. But if that's not the allowlist for min-publish-age then what is? What about MSRV?

Ed: MSRV is different, you can still resolve.

Josh: With MSRV set, I can do cargo update -p and will cargo update downgrade that?

Ed: I think it will

Josh: We should be consistent in the behaviour here

Ed: We should be consistent, but two questions: should cargo update error or not? And: should we have normal precedence for locked version or make them lover than everything else? We need to answer both questions and be consistent across all the states.

Jacob: We'll need a flow chart of all the different scenarios and restrictions. Start documenting what we've got.

Ed: Hopefully keeping it consistent won't be to hard

Arlo: I can see reasons for wanting both ways.

Ed: It feels weird to use "cargo update" to do downgrades

Arlo: How do I effectively downgrade to match the policies then?

Jacob: One option is delete lockfile and start over. The other is that we have the somewhat-deprecated `generate-lockfile` command. We could revive it with update being aware of the lockfile

Ed: Third option: wait three days

Josh: Fourth option: if you bump the version in `Cargo.toml`, cargo update would have to do that.

Ed: You'd get a cargo update error because there's no candidate error because the version is newer than min-publish-age

Ed: Should we error or not? Should we treat the dependency like normal or give it lowest priority?

Josh: This applies all the way down the chain, right? If one of your dependencies wants newer than three days dependency, cargo update will fail there too, right?

Ed: Yes

Josh: One thing I've seen attackers trying todo is yank every version other than my newest vulnerable version. If we just chose to treat min-publish-age as advisory, it would use the new backdoored version. That's argument against using it as just an advisory. But we have to give them some way to bypass it -- but how do we do that?

Ed: I'm not talking about changing the meaning of deny to fallback. I'm saying if you have something in the lockfile to put it back in the list.

Josh: So we wouldn't fail a resolve if you don't have a lockfile, you're just suggesting that if your lockfile already allows this version, then we can fall back to it. That's okay. We should apply that to MSRV too, then.

Ed: If you do `cargo update -p` on a dependency is, it will downgrade it. Should we error or at least keep a version rather than downgrading a aversion?

Josh: If we kept such a version from the lockfile, we could print a message.

Ed: The problem is where we do the rendering is different from when we make the decision. But there's at least a way to notify the user that soemthing about this version is suspect.

Josh: If we changed things so `Cargo.lock` is an allowlist, are we willing to do that consistently for min-publish-age and handling MSRV?

Ed: The most suspect place if we do this is `yank`. If you have a yanked package, right now we downgrade or if the version requirement is too high, we error instead. I'm fine with loosing up some of the `yank` stuff. There's some ecosystem pressure with yank. How much burden do we put on the community

Josh: There are two options here: (1) we make `cargo update` treat your lockfile as an allowlist across the board. (2) we say `cargo update` should be stateless and it shouldn't care with what's in your lockfile (unless you use the `-p` option). We do (2), what's the documented process 

Ed: A future possibility: the RFC said we could add an explicit allowlist later. I was hoping to reuse existing mechanisms. For some of the opt-outs, there's e.g. someone always trusting the author or wanting the latest to get a latest fix.

Josh: We could curate this for them. If we have an allowlist, we could automatically add things to it when you do `-p <version>`, we could even add a reason it was overwritten.

Arlo: I like the idea of cargo update allowing things in the lockfile. But I'd like to have ways to generate the lockfile.

Jacob: A flag that says "ignore lockfile" whose documentted behaviour is equivalent to deleting the lockfile is also ok

Josh: We have a lot of hypotheticals around ignoring lockfile and creating a new allowlist. Both will be a while. Given the current state is the RFC said "give an update and respect the lockfile", should we start updating the documentation and then figure out which solution we wish to offer?

## Disabled optional weak dependencies end up in `Cargo.lock`

- https://github.com/rust-lang/cargo/issues/10801

Weihang: there is a PR: <https://github.com/rust-lang/cargo/pull/16424>. I've kinda reviewed a bit and looks reasonable. We should probably add more tests first capturing some corner cases and then merge or iterate on that one.

Arlo: Is this the same attempt we talked about last time or is this new? Because that PR had serious fundamental flaws.

Jacob: I don't remember the last conversation. The fundamental issue here is it doubles down on the feature of the resolver that tracks other features. And that's currently not completely reliable. But that's not this PR's problem to fix.

Josh: I ran into this yesterday and I noticed a large community of people regularly hitting this and pointing at this issue. sqlx has a lot of optional features, some have weak feature dependencies on dependencies that they have. If any of those are enabled, we put it in Cargo.lock and require that they're resolved directly. And if you can't have those in the lockfile, you'll have a bad time.

Jacob: I attempted to fix this two years ago, but it's had little impact on our users. So as long as someone's moving things forward, I won't stop them. It felt to me that we didn't have the sound underpinnings to do that. But if someone wants to make progress, we should let them make progress.

Josh: We could take a lesson from pubgrub and trait solver: "we've spent a lot of times fixing issues in the ecosystem and performance issues and now we've fixed them and we're shipping what we have. If there are other issues, we can fix them"

Jacob: That's a good inspiration.

Jacob: I could commit to doing a code correctness review of this. What's scaring me is shepherding this through the follow-up. This needs a lockfile version bump. We have a bunch of things set up for the next lockfile bump that haven't merged yet. It may require a resolver bump. That usually requires a `-Z` feature to experiment. That's herding a lot of cats.

Daniel: I could dive into this but not until December, that's when I expect to have more free time.

Jacob: A bunch of people would be happy with just having a `-Z` flag even if it broke compatibility with everything else until we'll have figured that out
